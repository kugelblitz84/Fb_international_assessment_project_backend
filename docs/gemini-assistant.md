# Gemini assistant integration

## Configuration and startup

Installed official `@google/genai` **3.4.0**. Set GEMINI_API_KEY manually in local `.env`; never put it in Flutter or source control. Default model is the requested `gemini-3.5-flash-lite`, configurable without fallback. Missing key returns 503 ASSISTANT_DISABLED for chat while health/catalog/auth/booking continue. Model/key rejection returns ASSISTANT_CONFIGURATION_ERROR; no alternate paid model is selected. See [all environment settings](environment.md).

The installed SDK declarations and Google's [structured-output documentation](https://ai.google.dev/gemini-api/docs/structured-output), [GenerateContentConfig reference](https://googleapis.github.io/js-genai/release_docs/interfaces/types.GenerateContentConfig.html) and [model catalog](https://ai.google.dev/gemini-api/docs/models) were checked. Implementation uses `models.generateContent`, `responseMimeType:application/json`, `responseJsonSchema`, `systemInstruction`, `maxOutputTokens`, `abortSignal` and HTTP timeout. `retryOptions.attempts:1` means one attempt, without automatic retries. API syntax is also asserted with a fake SDK transport test.

## Architecture and grounding

New files under `src/features/assistant/`:

- `assistant.module.ts` composes existing CatalogModule, PlatformModule and PrismaModule.
- `http/assistant.controller.ts` applies optional auth, Zod request validation and no-store JSON responses.
- `application/assistant.service.ts` coordinates screening, context, provider timeout, output validation, catalog revalidation and server-generated price lines.
- `application/assistant-context.service.ts` reuses `CatalogService.listServices()`, `listCategories()` and `PlatformService.getPublicKnowledge()`.
- `application/assistant-usage.service.ts` bounds IP/user request windows and concurrent work.
- `data/gemini.service.ts` implements the replaceable `AssistantModel` contract using the SDK.
- `data/assistant-budget.repository.ts` atomically enforces shared daily spend limits using private reserved PlatformSetting keys.
- `domain/assistant.types.ts`, `assistant.schemas.ts`, `assistant.prompt.ts`, `assistant.error.ts` define contracts, validation, system instructions and safe error envelopes.

Modified backend files include app module/bootstrap, typed config, package/lockfile, environment example and documentation. No chat schema or assistant persistence is added. The daily counter stores only a date/count.

Context contains the complete current active catalog: UUID, name, description, category, type, original/effective BDT prices, duration, inclusions, featured/catalog availability, current offer and package component names/UUIDs/quantities. It also includes active category UUIDs/names, public policies/business hours and configured booking horizon/timezone. Images and internal database fields are omitted. Pricing comes from the same Decimal application service used by booking. Inactive categories/components hide packages; expired offers do not affect the context. Context JSON is capped at 48,000 UTF-8 bytes.

System instructions are separate from catalog and conversation data. User roles map to Gemini `user`; assistant history maps to `model`, but remains explicitly untrusted. There is no provider chat session, tools, arbitrary fetching or appointment write capability. For availability, the assistant directs users to existing booking pages for live slots rather than inventing times. No private appointment context is retrieved.

## Request, actions and factual checks

[Example response](examples/assistant.json) was generated by the real orchestration and DTO validator with a fake provider and seeded UUIDs. It is a fixture, not a successful live Gemini result. Regenerate with `GEMINI_API_KEY=documentation-fake-provider` and `npx ts-node scripts/export-assistant-example.ts` against a seeded development database.

```json
{
  "messages": [
    {"role":"user","content":"I want to clean my car."},
    {"role":"assistant","content":"What is your approximate budget?"},
    {"role":"user","content":"Around 1500 taka."}
  ]
}
```

POST `/api/v1/assistant/chat` accepts guests and valid optional bearer sessions. Invalid supplied tokens return 401 rather than downgrading to a guest. Reject system roles, unknown fields, empty messages, more than twelve messages, more than 2000 characters per message, more than 12,000 total characters, or a final assistant role.

Gemini generates `{text,actions}` only. The server supplies UUID message identity and assistant role. Runtime Zod validation is stricter than provider JSON Schema: only `serviceDetails` plus required UUID serviceId, or `browseServices` plus optional UUID categoryId. Unknown fields, paths, URLs, action types and invented/stale IDs are rejected; duplicates are removed and at most four actions returned. Packages use their own ordinary Service IDs. Flutter resolves these through its existing AppRoutes and catalog map, not text/Markdown parsing.

Model free text is not trusted for arithmetic. Detected numeric, monetary, offer, time and link claims are replaced with neutral guidance; exact current price/original-price/duration lines are constructed on the server from a second public-context read after generation. Recommendation cards also use a refreshed live catalog. Model text cannot change prices or trigger appointment operations. Structured schema validation does not prove every free-text statement or inferred budget/diagnostic recommendation is correct; mechanical diagnosis and personal booking management remain outside scope. Unknown semantic claims and sensitive details cannot all be recognized by pattern screening. Treat the assistant as guidance and use catalog cards/booking pages as authoritative.

## Reliability, quota and privacy

Defaults: 5 requests/minute and 20/hour per IP and per authenticated user; two concurrent calls per process; 100 daily admitted requests shared across instances through PostgreSQL. The daily cap resets by UTC date and survives restarts. The default is not Google's quota: configure it at/below the actual project's free-tier/billing allowance. Zero daily budget disables admissions. Short-window rate limits and concurrency are process-local; multiple replicas require shared ingress controls. Denied or failed admitted requests may still consume the conservative request budget. No automatic retries are made.

End-to-end provider waiting is bounded by the configured timeout (20 seconds default) and AbortController. SDK HTTP timeout and 1500-token default output cap also apply. Timeout releases local capacity; aborting a client request cannot guarantee the provider stopped processing or charging it. Context/output size and limiter maps are bounded. Output codes distinguish disabled configuration, unavailable model/key, quota, rate/concurrency limits, timeout, blocked safety output, empty/malformed JSON and network/provider failure. [API error table](api.md) lists exact statuses/codes. No raw provider exception, key, prompt, token or request body is logged/returned by assistant code.

Only public platform/catalog data goes into context. User ID/IP are used locally for limits; they are not forwarded. No profiles, appointment records, credentials, registration numbers or session metadata are read for Gemini. The entire submitted history is screened for common email, credential/token, phone and vehicle-registration patterns before forwarding. Rejected sensitive input returns ASSISTANT_SENSITIVE_INPUT and is not sent. Screening cannot detect all personal names/details; the UI and this notice instruct users not to include them.

Messages are processed by Google. Free-tier inputs/outputs may be used for product improvement; assess the selected account's [Gemini API terms](https://ai.google.dev/gemini-api/terms) before using real data. The backend stores no conversation history; Flutter keeps conversation state in memory and resets it on account changes. Never paste personal or confidential information into this public service assistant.

## Flutter integration and checks

The adjacent frontend now has assistant/catalog endpoints, strict model/action deserialization, bounded recent-history serialization, live Dio adapters, optional guest/authenticated requests, safe error-code mapping and explicit demo mode. Public catalog calls omit bearer credentials. Browser auth transport acquires CSRF tokens for refresh/logout; native cookie transport is preserved. Cards show current catalog images, names, effective/original prices, duration and service/package navigation. Existing controller identity/generation checks discard late responses; retry, clear and shell state remain. A failed catalog load no longer leaves `sending` stuck.

Backend automated checks: 17 unit tests and five integration tests, including fake provider/SDK scenarios, HTTP optional auth, missing configuration, public-only context, global daily counter races, authentication, catalog and appointment database constraints. Frontend analysis and tests cover strict response contracts, bounded history, real UUID catalog resolution, guest/signed-in requests and existing state/navigation/responsive flows. See the final implementation report for executed results.

Live Gemini verification: **not performed; no API key was configured**. No claim is made that the configured model has completed a live request. After configuration, start the backend and test a harmless public question:

```powershell
$body = @{ messages = @(@{ role='user'; content='Suggest an existing package under 2000 taka.' }) } | ConvertTo-Json -Depth 5
Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/v1/assistant/chat -ContentType application/json -Body $body
```

Then check a multi-turn follow-up, offers, policy questions and valid recommendation cards with Flutter `API_BASE_URL` including `/api/v1`. Confirm provider quota/model availability in the configured project. Live native/browser cookie behavior and platform deployment are separate manual checks. No automatic model substitution, chat-history storage, streaming, vectors or autonomous booking was introduced.
